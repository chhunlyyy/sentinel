## How the tests will run

- Unit scenarios: stdlib `unittest` in `tests/`, one test per scenario (one subtest per Examples row), test names carry the AC id (for example `test_AC_VER_03c_each_rule_gives_its_reason`). Skill scenarios (`AC-ARC-03l`, `AC-ARC-03m`, `AC-VIS-03d`, `AC-VIS-01b`, `AC-VIS-05a`, `AC-VIS-05b`, `AC-VIS-05d`) read the skill files and check named sections and phrases.
- Integration scenarios: new checks in `sentinel/scripts/selftest.py` or `tests/` with a temporary workspace, named after the AC id. Agents are fake CLIs under `runners`, as in Phases C and D. Reviewer and QA fakes write a `result.json` with the findings the scenario names.
- Test profile `fake-junit` (Phase D) gains `build`, `lint`, `typecheck`, `mutate`, `audit` and `docs` commands that call one fake check tool. Each scenario scripts its exit code, stdout and JUnit XML per command and repo. The migration lane pattern is `(^|/)db/migration/`.
- Fixtures: runs in VERIFYING, REVIEWING or COMPLETED, cycles, evidence rows, rounds, findings and approvals are written through engine fixture functions. Labels as in Phases C and D.
- Human at a terminal: `sentinel accept`, `run export` and `run import` run under a pseudo-terminal (`pty` module) for the TTY cases, and with stdin from a pipe for the non-TTY cases, as Phase B does for `approve`. R20 decisions (resume, waive a finding, approve a destructive migration) call the engine function with actor `human` and channel `tty`, since no CLI exists yet (point 12).
- End-to-end scenarios `AC-ARC-03n` and `AC-ARC-03o`: a test script plays the orchestrator by mapping each `next` step kind to the one action the skill names, and a scripted human approves through a pseudo-terminal. The script records every command it ran.
- Golden files for `AC-OPS-04a` (Claude agent files) and `AC-VIS-05b` (triage matrix) are taken from the commit before Phase E starts and stored under `tests/fixtures/`.
- Timing as in Phases C and D: no test waits longer than 15 seconds. Concurrency scenarios use two processes against the same `.sentinel/sentinel.db`.
- Exit codes: `sentinel verify` 0 all required checks passed (R14 applied), 1 a check failed and fix tasks were queued, or a database error, 5 refused, 6 run went to NEEDS_HUMAN. `sentinel accept`, `run export`, `run import` 0 done, 1 database error, 5 refused. `sentinel report` 0 or 5. Order as before: 3 over 6 over 1.
- Gate for Phase E completion: all Phase E tests pass, all Phase A to D tests and the 95 baseline selftest checks pass, evidence recorded in `IMPLEMENTATION_STATUS.md`.

## Open points for the reviewer

Each point is a choice made where the documents conflict or say nothing. Approving this set approves these choices.

1. **Check kinds.** Evidence kinds for verification: `targeted` (union of the targeted tests of the repo's accepted cycles), `test` (full suite), `build`, `lint`, `typecheck`, `hygiene` (the `release_checks` items of `release_check.py`: debug output, TODO, comments, test infrastructure), `scope`, `secret` (scrubber patterns plus gitleaks when installed, as today), `deps`, `mutation`, `migration`, `extra` (from `verification.extra`), and for docs-only runs `docs_links` and `docs_build`. `targeted`, `hygiene`, `extra`, `docs_links` and `docs_build` are new names next to the list in `data-architecture.md`. Each row is per repo; repos without changes get only a `scope` row.
2. **Checks per tier.** Tier 1: targeted, test, build, lint, typecheck, hygiene, scope. Tier 2 and 3 add secret and deps. Tier 4 adds mutation (`verification.mutation`, default `tier4`). Migration safety runs at any tier when a file under the profile's migration lane changed (`migration_check: auto`), not only from tier 3 as the orchestration table says, because a schema change at a low tier is exactly the risky case. The "docs" item of tier 3 in that table is read as the docs review stage, not a check. Docs-only runs: docs_links (relative Markdown links of changed docs resolve), docs_build when the repo sets the new key `commands.docs`, scope.
3. **Not run is not missing.** An empty command gives a row `not_configured`; a check listed in the new key `verification.disabled` gives a row `disabled`. Neither runs a command, neither counts as missing evidence, and the report lists both under "not run". `test` and `scope` cannot be disabled (config invalid). A code repo with no test command, or a tier 4 repo with no mutate command, sends the run to NEEDS_HUMAN before any check runs. Schema: `verification` gains `mutation` (`tier4|always|never`), `migration_check` (`auto|always|never`), `disabled` (list) and `extra` (the `extra_checks` rule shape); top-level `extra_checks` keeps working for `release-check`.
4. **Full suite against the baseline.** The `test` check fails only on a failure outside the Phase D baseline failing set; baseline failures that still fail are listed as pre-existing, ones that now pass as fixed. No report plus a non-zero exit is `unknown`; an environment pattern is `environment`; both go to a human, never to an agent.
5. **Scope check.** The diff from each repo's baseline SHA (tracked and untracked, content-hashed) against the union of the write scopes of every completed task of the run (cycle, fix and review tasks). Paths changed before the run with an unchanged hash are not blamed. HEAD moving is a failure. Config, agent and skill files are always violations. A scope failure is never routed to an agent; nothing is reverted without the human.
6. **Rounds and storage.** Evidence rows gain `round` and `repo_id`; a new `verification_rounds` record holds start, finish and `interrupted`. Rows are written as each check finishes (so progress is visible); a round counts only once it has a "finished" record, and acceptance reads the latest finished round. One verification at a time per run (`E_LOCKED`); `verify` is refused while any task of the run is RUNNING. A stale round lock from a killed process does not block the next call.
7. **Routing of failed checks.** The run stays VERIFYING (R14 "on failure"). One fix task per failing repo per round, with every failure of that repo in its brief: role `tdd_green` (production globs, approved tests read-only) for test, targeted, build, lint, typecheck, hygiene, secret, deps, extra and `applied_migration_changed`; role `hardener` (test globs, approved tests read-only) for mutation survivors. A failure located only in an approved test file goes to a human. Fix tasks belong to no cycle; trace links `evidence -> task` and `task -> file` keep the chain. `limits.release_check_rounds` (default 3) is the total number of rounds: at cap 3, rounds 1 and 2 get fix tasks and a failing round 3 goes to NEEDS_HUMAN.
8. **Migration safety is a new check.** Added files under the migration lane are scanned for destructive statements (`DROP TABLE`, `DROP COLUMN`, `TRUNCATE`, `RENAME`, `DELETE` without `WHERE`): classification `destructive`, NEEDS_HUMAN by policy `destructive_migration`. A human approves it by file sha256 through an R20 decision, stored as an approval with the new gate name `migration`; an edit voids it. A migration file that existed at baseline and changed is `applied_migration_changed` and is routed as a defect.
9. **Dependency check.** When a manifest changed, `deps` runs the new profile or repo command `audit` (for example `npm audit`) and lists the added dependencies in the report and on the `accept` screen; with no `audit` command the row is `not_configured`. The `release-check` notice stays.
10. **Review stages.** Created at R14 as a chain: reviewer, qa, promotion, docs, and at tier 4 rollout and retrospective, each depending on the one before. Tiers 1 and 2 have none, so `next` applies R15 straight after R14. Write scopes: reviewer, qa and rollout none (output in `result.json`), promotion `.sentinel/shared/regression/**`, docs `<repo>/docs/**` and `<repo>/CHANGELOG.md` for each run repo, retrospective `.sentinel/shared/proposals/**`. QA mode `targeted` at tier 3, `full` at tier 4.
11. **Findings.** Stored from `result.json` `findings`. Minor findings are kept open and never routed. A blocker or major sends the run back with R16 and a new cycle for the behavior group whose cycle changed the finding's file (one cycle per group even with several findings; no owner means NEEDS_HUMAN). Downstream review tasks are cancelled. A finding is resolved when its cycle is CYCLE_ACCEPTED and the next verification passes; the next reviewer gets the resolved list to re-check and may raise new findings. QA findings gain an optional `category` (`code_bug` default, `spec_gap`); a spec gap goes to a human, who changes the spec (R17) or decides otherwise. The `agent-result-v1` schema gains `category` as an optional finding field.
12. **Caps, waivers and R20.** `limits.review_rounds` and `limits.qa_rounds` count R16 transitions per source; cap N allows N. At a cap the run goes to NEEDS_HUMAN. A human can waive an open finding through an R20 decision; the run then completes but acceptance is "rejected" (VER-03: required reviews open). There is still no CLI for R20 decisions (resume, waive, approve a migration file, approve a real-data clone): tests call the engine function with actor `human`, channel `tty`. Proposal: a human-only TTY command `sentinel resolve <slug> [--waive <finding>] [--approve-file <path>] -m <comment>` in Phase E, or leave it to the Phase F control endpoint.
13. **Tier rise on a review blocker.** The 0.1 rule "a blocker in tier 2 or 3 re-triages upward" is kept for tier 3: the tier becomes 4, so the security gate applies and the run goes to NEEDS_HUMAN before R16 executes anything. Alternative: drop the rule for version 2 runs.
14. **Acceptance computation.** Reasons, in this fixed order: specification approval, Gherkin approval, cycles incomplete, required tests fail, verification evidence missing, scope exceeded, required reviews open (open or waived blocker/major, or a review task not COMPLETED), required human approval missing (security at tier 4, migration). All reasons are reported. R15 also writes the report, records final SHAs and releases the slug lock (today only CANCELLED and FAILED release it).
15. **`sentinel accept`.** Needs a TTY and the first 8 hex characters of the report.json sha256 (the report is what the human accepts; the HTTP body later sends the full hash). `--reject` needs `-m`. Before a confirmation the engine re-hashes approvals and evidence outputs (stale or changed: refused, the human can still reject). One confirmation only; a confirmed run can later be rejected; a rejected run can never change. Refused calls are audited (`acceptance_refused`). Inside a task process (`SENTINEL_TASK_ID`) the refusal is `E_ACTOR`. `next` on COMPLETED keeps kind `done` and exit 0 (Phase C `AC-ARC-03a`) and adds human acceptance "pending" with the `sentinel accept` command.
16. **Report.** Sections: execution, specification, gherkin, agents, cycles, verification, regression, findings, changed_files, acceptance, trace, cost. report.json has no wall-clock time (it names the last event id) so it is reproducible and can be accepted by hash; it is stored as an artifact of kind `report`. Unreported tokens and cost are null with a reason; totals are marked partial. `report` is refused for 0.1 runs.
17. **Export and import format.** `<slug>.sentinel-run.tar.gz`, mode 0600, never overwritten: `manifest.json` (format `sentinel-run-bundle-v1`, Sentinel version, registry schema version, slug, sha256 and size of every file, excluded paths), `rows.json`, `run/`, `shared/specs/<slug>/`. Never included: `.sentinel/cache/` (live logs, QA storage), `.env*`, `sentinel.db`, `server.json`, other runs, repo source. Binary files are excluded and listed. Everything else passes the scrubber with the workspace's `.env` values, and `scrub --check` must pass on the result. A scrubbed artifact carries the scrubbed sha256 plus `scrubbed` and the original sha256. If scrubbing would change an approved spec or feature file, export is refused, because the approval could no longer be verified. A run with a RUNNING task is not exported.
18. **Export and import are TTY actions.** The security doc says exports "need `--yes`"; the CLI contract says actor H. Choice: both need an interactive terminal (refused `E_NOT_TTY` otherwise, `E_ACTOR` inside a task process); `--yes` only skips the confirmation question. Import checks format, schema version, every hash, unlisted files, unsafe entries (`..`, absolute paths, symbolic and hard links) and the slug (registry row, run folder or shared spec folder) before writing; it unpacks into a temporary folder and writes rows in one transaction. Rows keep their ids; events get new ids with the original id in the payload. An active imported run takes the slug lock; a missing baseline commit makes `next` apply R21. Residual risk: the manifest is not signed, so the hashes catch corruption and casual edits, not someone who rewrites a file and the manifest together.
19. **Publishing.** Version 2 runs never push to the shared repo by themselves, even with `state.auto_sync_push: true`; promotion writes only the local shared folder, and publishing stays a human `sentinel sync push <slug> --yes` (policy `publish`). This changes behavior for configs that turned auto push on, for version 2 runs only.
20. **TDD-09 is not in this set.** Phase D left it for Phase E ("needs QA"). Proposal for a short addendum: in a client repo with `no_permanent_frontend_tests`, the behavior group's cycle skips Red; the QA task's scenario steps for that group are the Red evidence (must fail before Green, pass after), and the run and report record the exception. Approve this set without it, or ask for the addendum before building PE-01.
21. **Skill and adapters.** The rewritten `SKILL.md` has sections "Version 2 runs" (the `next` loop of `orchestration-architecture.md` section 6 plus the stop-at-human rule) and "Legacy runs (0.1)" (today's text, kept so the 95 selftest checks still find their phrases). `pipeline.md` keeps the triage matrix byte for byte, since the engine computes the tier from it. No agent files are generated for the new roles: native tasks carry their own `prompt.md`, so `.claude/agents` stays byte-identical. The AGENTS.md block gains the `next`, `task run` and `task complete` lines. `sentinel-resume` and `sentinel-status` gain one line each for version 2 runs.
22. **Migration.** Phase E needs a registry migration: evidence `round`, `repo_id`; `verification_rounds`; finding `category`, `cycle_id`, `decided_by`, `comment`; approval gate values `migration`, `real_data_clone`, `acceptance`; artifact `scrubbed`, `original_sha256`. Numbers are taken in merge order after Phases C and D.
