# Implementation Risks

| ID | Risk | Impact | Likelihood | Mitigation |
|---|---|---|---|---|
| R1 | **Approval forgery.** Agents run with the user's shell and can call `sentinel approve` themselves. A local CLI cannot fully prove a human acted. | Breaks the central guarantee of both gates | High without mitigation | TTY-only approval with typed hash confirmation; deny rules for `sentinel approve*` in generated agent configs; approver identity recorded; audit log. Document the residual risk. A stronger guarantee needs the dashboard's authenticated channel, with a secret the agent cannot read. |
| R2 | **Orchestrator is an LLM.** The skill drives the flow; the engine can only refuse. A model can ignore instructions and edit files directly without calling Sentinel. | Gates become advisory | Medium | Make every acceptance depend on engine-written evidence (Sentinel runs the tests, hashes match). A run without evidence can never reach `acceptance_status = accepted`, whatever the agent did. |
| R3 | **No pre-execution sandbox.** Provider CLIs (`acceptEdits`, Antigravity accept-edits) can run any command. "Never allow unrestricted shell" is not enforceable by Sentinel alone. | Scope and command policy are detective, not preventive | High | Post-hoc diff checks per task; optional worktree isolation; pass provider-native permission flags where they exist; state the limit in `docs/security.md`. |
| R4 | **CLI compatibility.** Stricter `run update` and new required gates break existing skills, scripts and runs in progress. | Existing users blocked | High | Version the run schema; old runs (no `schema_version`) resume in legacy mode; new runs use the engine. Selftest keeps all 95 legacy checks. |
| R5 | **Tier 1 friction.** Two human gates for a one-line fix. | Users bypass Sentinel | High | Decision B5: one combined approval for tier 1. |
| R6 | **Red failure classification across stacks.** Distinguishing an assertion failure from a compile or environment failure differs per stack (Gradle, Jest, pytest, Flutter). | False accept or reject of Red | Medium | Per-profile patterns plus a baseline comparison (test passed or was absent before, fails now, others unchanged). Unknown patterns go to `NEEDS_HUMAN`, never auto-accept. |
| R7 | **Scope creep.** The two specs together describe a multi-quarter platform. | Nothing ships | High | Core release first (B1). Each phase gated, each with an exit test. |
| R8 | **Gherkin vs project test frameworks.** Most target repos (Spring, Next.js, Flutter) do not use Cucumber. | Red tests cannot "execute" `.feature` files | Medium | Approved Gherkin is the contract; Red writes native tests that reference scenario IDs; traceability checks the references, not a Cucumber runtime. |
| R9 | **Cross-machine resume vs privacy.** Run records hold code excerpts and logs; pushing them to the shared repo widens exposure. | Data leak | Medium | Export bundles are opt-in, scrubbed, and never auto-pushed. |
| R10 | **No unit-test framework.** All 95 checks are end-to-end in `selftest.py`. A state machine needs fast unit tests. | Slow feedback, weak TDD evidence for Sentinel itself | Medium | Add stdlib `unittest` tests under `tests/` (no new dependency), keep selftest as the integration suite. |
| R11 | **Version naming.** Package is `0.1.0b7`; plan says `1.1.0`. | Confusing release history | Low | Decision B7. |
| R12 | **Dashboard security surface.** A local service that launches processes and reads repos is an attack surface (CSRF, DNS rebinding, token leakage). | Local code execution | High (when built) | Deferred to its own design gate: loopback-only bind, random per-session token, origin checks, allow-listed operations only. |
