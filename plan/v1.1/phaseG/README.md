# Phase G: Dashboard UI (Gherkin for review)

Scope (from `SPEC.md`, `IMPLEMENTATION_STATUS.md` rows PG-01 and PG-02): the React + TypeScript + Vite single-page app of G1 Q1, built at release time into `sentinel/dashboard_dist/` inside the wheel and served by the Phase F server at `/`. It is local only and talks only to `/api/v1` and the SSE stream `/api/v1/events` of Phase F (`plan/v1.1/phaseF/README.md` and its features are the API contract: routes, envelopes, session and CSRF flow, the `confirmation` field of decisions, the `resync` stream message). Requirements: DSH-01 to DSH-06 (navigation, first-run guide, readiness states, no success before the API confirms, live updates with reconnect, offline), INS-02 to INS-07 (installation, health checks, running server, actionable errors, allow-list, doctor parity), PRJ-02 and PRJ-04 (project list, read only), REP-03 and REP-04 (repository details and validation), CFG-01, CFG-02, CFG-05, CFG-06, CFG-08 (configuration center, read only, with history and diff), TSK-01 to TSK-03 (task list and creation; Q2: dashboard-created tasks are queued for the AI tool), SPA-04 to SPA-06, SPA-08, GHA-04, GHA-05, SEC-03 (approval center), MON-01 to MON-03 (run graph, cancel, resume and retry, log tail), TDD-06, VER-02 to VER-04, GIT-01, GIT-03, TRC-01, TRC-02 (quality views, final acceptance, diffs, trace), ANL-02 (missing values shown as missing), SEC-01, SEC-06, SEC-07 (session handling, scrubbed diffs, audit view), OPS-01 (assets in the wheel), TST-01 (earlier tests unchanged). Accessibility and safe rendering of untrusted content are covered under DSH-01 and INS-06 (no requirement names them; see point 9).

- PG-01: shell, session, errors and own-origin rule (`app_shell_session.feature`), installation, health checks, readiness and first-run guide (`installation_readiness.feature`), the read routes Phase G adds to the server (`server_read_routes.feature`), projects, repositories, configuration center and audit (`projects_config_views.feature`), build into the wheel, offline and contract fixtures (`build_packaging.feature`).
- PG-02: task list and creation (`tasks.feature`), approval center (`approval_center.feature`), monitoring with live updates (`monitoring_live.feature`), TDD cycles, verification evidence, final acceptance, diffs and trace (`quality_trace.feature`), accessibility and XSS for every screen (`accessibility_xss.feature`).

Not in Phase G: every mutating operation Phase F did not build — creating, registering, editing, archiving or removing projects; adding, editing, removing, reordering, cloning or inspecting repos; saving, validating, restoring, importing or exporting configuration; the global configuration screen; the directory picker; provider tests; publishing (point 1). Also not in Phase G: the pause and "request intervention" controls (dropped, not shown); task attachments, templates (TSK-04) and provider preference (point 6); notifications NOT-01 to NOT-03 and analytics ANL-01 (Phase H); agents, providers, reports and users screens (point 7); multi-user roles (SEC-05 LATER). The UI depends on Phase F (and the engine functions of Phases C to E behind it); e2e tests run against a fake API server whose fixtures are recorded from the real Phase F server.

## How the tests will run

- Tooling, all pinned in `dashboard/package-lock.json`: Vitest with React Testing Library and jsdom for `@unit` scenarios; Playwright Test with `@playwright/browser-chromium` (Chromium is downloaded by `npm ci`, into the npm cache folder, not at test time) for `@e2e`; `@axe-core/playwright` for the accessibility scans; ESLint with `eslint-plugin-react` and `eslint-plugin-jsx-a11y`; TypeScript `tsc --noEmit`. After `npm ci` every command (`npm test`, `npm run e2e`, `npm run lint`, `npm run typecheck`, `npm run build`) runs with no network; `AC-DSH-06g` proves it in a network namespace with only loopback. Test names carry the AC id (for example `AC-SPA-05e approving the specification`); Examples rows are `test.each` rows.
- Fake API server: `dashboard/e2e/fake-api/` is a small Node HTTP server started by Playwright's `webServer` on 127.0.0.1 with a free port. It serves the built `sentinel/dashboard_dist/` and the Phase F routes from JSON fixture sets (`two-projects`, `fresh-install`, and per-scenario overrides set through a test-only control route that the real server does not have). It sends the Phase F security headers, cookie and CSRF rules and SSE format (ids `<project>:<id>`, `resync`, heartbeats), and it can delay, drop, or fail any route as the scenario says. Event-stream scenarios push messages through the control route.
- Contract fixtures: the Python test `tests/test_dashboard_fixtures.py` (`AC-DSH-06i`) starts the real Phase F server against fixture workspaces with a fixed clock and fixed ids, calls every route the fake serves and compares with the stored fixture, ignoring a listed set of volatile fields. It runs in the normal Python suite, so a Phase F change that breaks the UI's view of the API fails in Python first.
- Server read routes (`server_read_routes.feature`): stdlib `unittest` in `tests/test_server_read_routes.py`, as Phase F does: temporary HOME, `sentinel dashboard --no-open` under a pseudo-terminal, `http.client` with explicit Host headers. Fake runners and fixture workspaces as in Phases C to F; `AC-DSH-03e` uses commands that write a marker file.
- Build and wheel (`build_packaging.feature`): `tests/test_dashboard_wheel.py`, skipped with a recorded reason when Node is not installed; it runs in the release job. Steps: `npm ci` and `npm run build` in `dashboard/` (Vite `base: './'`, output `../sentinel/dashboard_dist`, no source maps, a manifest of every file with its sha256 and the source hash), `uv build`, install the wheel into a temporary tool folder with a `PATH` that has no `node` or `npm`, start the server under a pseudo-terminal, load `/` in Playwright and check every asset. `AC-OPS-01e` checks the release guard (`SENTINEL_RELEASE=1`) in the build backend hook. The wheel includes `sentinel/dashboard_dist/**` through the existing package data rules; Node is never a runtime dependency (OPS-01).
- No CDN or network at runtime: the bundle is scanned for remote URLs (`AC-DSH-06f`), Playwright records every request of full sessions (`AC-DSH-06e`), the page runs under the Phase F CSP with no violation (`AC-INS-06f`), fonts are the system font stack, and Phase F `AC-DSH-06a` and `AC-DSH-06b` are re-run with the real assets installed.
- Accessibility: axe-core WCAG 2.1 A and AA rules on each listed screen in both themes, failing on "serious" or "critical"; contrast of the theme tokens computed in a unit test; keyboard-only flows driven with `page.keyboard` only. A manual screen-reader check (Orca on Linux or VoiceOver on macOS) of the approval flow is recorded in `IMPLEMENTATION_STATUS.md` (TST-04 style manual evidence).
- XSS: payloads are put in every fixture field that reaches the page; the test asserts the literal text, no new elements, no dialog (`page.on('dialog')`), no request to `evil.example`, and a CSP report count of zero. `AC-INS-06e` is an ESLint plus grep check over `dashboard/src`.
- Timing: no e2e test waits longer than 15 seconds; slow and dropped answers use the fake server's controls and Playwright's clock where possible. The performance limits (`AC-GIT-01d`, `AC-GHA-04g`, `AC-MON-01i`) are measured in the normal suite.
- Gate for Phase G completion: all Phase G tests pass, all Phase A to F tests and the 95 baseline selftest checks pass, the release wheel built from a clean checkout passes `AC-OPS-01b`, the manual screen-reader check is recorded, evidence in `IMPLEMENTATION_STATUS.md`.

## Open points for the reviewer

Each point is a choice made where the documents conflict or say nothing. Approving this set approves these choices.

1. **Server work in Phase G is read only.** Phase F built a subset of the contract and left the rest to Phase G; the brief says the UI talks only to the Phase F API and the configuration center is read only unless the API supports editing. Choice: Phase G adds only the GET routes the screens need — `/installation/health`, `/projects/{pid}/readiness`, `/projects/{pid}/repositories`, `/projects/{pid}/configuration`, `/configuration/history`, `/configuration/diff`, `/tasks/{slug}/changes`, `/changes/diff` — and no mutating route (`AC-INS-06a`). Creating and registering projects, repo changes, config save, validate, restore, import and export, the directory picker, provider tests and publishing stay 404. The UI shows the command or file to use instead. Consequence: DSH-02 steps "create project", "add repos" and "configure", PRJ-03 to PRJ-05, REP-02, REP-05, CFG-03, CFG-04, CFG-07, INS-08 and PRV-01 to PRV-03 and AGT-08 are not met in 1.1.0 by the dashboard. Proposal: a Phase G2 with its own Gherkin for the write routes (clone URL checks, allow-list paths, config save with `base_sha` and `config_versions`, audit), or move these requirements to LATER.
2. **Config history is what config_versions holds.** Today `config_versions` rows are written as run snapshots (scope and sha256), not on each edit. The history view lists those rows plus the current file (`diff?b=current`). A full edit history needs the write routes of point 1.
3. **Readiness never runs project commands.** A GET must not run build or test commands. Readiness checks paths, git state, branch, write permission, profile, schema, provider install status and that each command's executable is on PATH; anything further is `not_checked`, shown as "Not checked", never "Validated". The readiness answer and its five states are new server shapes (state names in snake case).
4. **Health checks are the doctor checks.** `/installation/health` calls the same function as `sentinel doctor` (INS-07) and adds `required`, `status` and `fix` per item. If `doctor` does not have such a function yet, Phase G extracts it without changing the CLI output (guarded by the selftest checks).
5. **Hash routes.** Screens use `/#/...` so the Phase F static handler needs no history fallback. Alternative: a fallback of unknown non-`/api` paths to `index.html` in the server.
6. **Create task fields are the Phase F body.** The form sends `slug`, `request`, `type`, `repos`, `priority`, `tier`, `ticket` only, because Phase F refuses unknown fields. Attachments, templates (TSK-04) and provider preference are not in Phase G; they need body fields and storage that no phase defines yet. Proposal: Phase H or LATER.
7. **Navigation is trimmed to what works.** The menu has Overview, Projects, Tasks, My Approvals, Runs, Quality and Settings (installation, runtime, health). Notifications and Reports belong to Phase H; Agents, Providers and Users and Permissions have no API and are not shown rather than shown empty. DSH-01 is therefore met only in part until Phase H.
8. **Approval details.** The confirmation field is never pre-filled and nothing copies the prefix into it, but paste is not blocked, because blocking paste harms people who use assistive input; the server cannot prove typing anyway (Phase F point 1, residual risk R1). Comparison is exact and case-sensitive on lowercase hex. Reject of an approval and reject of the run ask a second time. A stale answer (`E_APPROVAL_STALE`) is never retried with the new hash; the reviewer must load and read the new version.
9. **Accessibility and XSS have no requirement id.** They are tested under DSH-01 (navigation for every user) and INS-06 (the browser never runs anything it was not built to run). Target: WCAG 2.1 AA for the screens of this phase, checked by axe-core plus a recorded manual screen-reader pass. Proposal: add `DSH-07` (accessibility) and `SEC-09` (untrusted content rendered as text) to `SPEC.md` at release.
10. **Specification text is shown as plain text.** No Markdown renderer is used for agent-written content, so no link or HTML can come from it (`AC-INS-06d`). Headings and lists stay readable as monospace text. Alternative: a Markdown renderer with HTML disabled and links rendered as text, at the cost of one more dependency to keep safe.
11. **Live updates refresh, they never patch.** An event only marks views stale; the page re-fetches with a short coalescing delay (at most 3 requests for a burst, `AC-DSH-05i`), and the state shown is always the REST answer. Controls and decision buttons are disabled while the stream is disconnected, so a decision is not taken on a view that may be stale.
12. **Report hash for acceptance.** The acceptance panel needs the report.json sha256 that `POST /acceptance` checks. Choice: it is read from the `GET /tasks/{slug}/report` answer (`sha256` next to the report). If the Phase F answer does not carry it, Phase G adds that field.
13. **Fake API with recorded fixtures.** E2E tests run against a Node fake, not the Python server, so they are fast and can inject faults; `AC-DSH-06i` keeps the fixtures equal to real answers, and `AC-OPS-01b` runs the real server once end to end. The fake has a test-only control route; it is never part of the wheel.
14. **Chromium through npm.** `@playwright/browser-chromium` downloads the browser during `npm ci`, which makes "offline after `npm ci`" true. Distributions without a Playwright-supported glibc can set `launchOptions.executablePath` in the Playwright config to a system Chromium.
15. **Release build guard.** The wheel build refuses stale assets only when `SENTINEL_RELEASE=1`, so developers without Node can still build and test the Python package (they get the Phase F placeholder page).
