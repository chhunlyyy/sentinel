## How the tests will run

- Unit scenarios: stdlib `unittest` in `tests/`, one test per scenario (one subtest per Examples row), test names carry the AC id (for example `test_AC_SEC_01l_host_header_checked`). Status-table scenarios (`AC-API-03c`, `AC-API-03d`) call the server's error mapper directly; `AC-API-03h` inspects the route table.
- Integration scenarios: `tests/test_server_*.py`. Each test sets `HOME` (and unsets `XDG_CONFIG_HOME` unless the scenario sets it) to a temporary folder, writes `projects.json` through the code under test or a fixture, and starts the server in a child process with `sentinel dashboard --no-open` under a pseudo-terminal (`pty` module), as Phase B does for `approve`. The test reads the port and token from server.json. Requests use `http.client` against `127.0.0.1` with an explicit `Host` header so wrong Host and Origin values can be sent. In-process server tests (for fault injection and the error mapper) start the same `ThreadingHTTPServer` on a thread with port 0.
- Event stream tests read the raw `text/event-stream` lines with `http.client`. The server accepts test-only settings for the poll interval, heartbeat interval and slow-client timeout through environment variables read only when `SENTINEL_TEST_MODE=1`; defaults are 500 ms, 15 s and 10 s.
- Agents are fake CLIs under `runners`, as in Phases C to E. Fixtures put runs in a state through engine fixture functions. Labels as in Phases C and D.
- Database faults (`AC-SEC-03u`, `AC-MON-02i`, `AC-API-02i`) use the registry fault hook of Phases C to E, or a read-only or removed database file.
- Concurrency scenarios use two processes (a pseudo-terminal `sentinel approve` or `sentinel task run` against an API call), started together behind a barrier. Each asserts the single winner from the registry rows and events, never from timing.
- `AC-DSH-06a` runs the server under `sys.addaudithook` in a child process and records `socket.connect` and `socket.getaddrinfo`. `AC-TST-01g` uses `python -X importtime` or a `sys.modules` check.
- `AC-SEC-01b` reads the listening sockets of the server pid from `/proc/net/tcp` and `/proc/net/tcp6` on Linux and with `lsof` on macOS (skipped with a recorded reason when neither is available).
- Timing: no test waits longer than 15 seconds; performance scenarios (`AC-MON-01d`, `AC-API-02k`) run in the normal suite with the stated limits.
- Exit codes of `sentinel dashboard`: runs in the foreground until stopped (0 on SIGINT or SIGTERM); 0 after attaching; 1 port in use, broken projects.json or another start failure; 2 usage; 5 refused (`E_ACTOR`, `E_NOT_TTY`).
- Gate for Phase F completion: all Phase F tests pass, all Phase A to E tests and the 95 baseline selftest checks pass, the security tests of `security-architecture.md` section 8 that belong to Phase F routes pass, evidence recorded in `IMPLEMENTATION_STATUS.md`.

## Open points for the reviewer

Each point is a choice made where the documents conflict or say nothing. Approving this set approves these choices.

1. **Dashboard decisions carry the full hash and the typed prefix.** The security doc asks for the full hash in the body; the brief and SEC-03 ask for the prefix and a confirmation. Choice: `POST /tasks/{slug}/approvals` takes `{gate, sha256, confirmation, decision, comment}` and `POST /tasks/{slug}/acceptance` takes `{sha256_of_report, confirmation, decision, comment}`. `sha256` is 64 lowercase hex characters; `confirmation` must equal its first 8 characters (the value the human typed in the UI). The server passes the full hash to `Engine.decide` (or the Phase E acceptance function) with actor `human`, channel `dashboard`, approver the OS user of the server process and the git `user.name`. Refusals before the engine call (bad hash or confirmation, missing field) are audited as `approve_refused` like engine refusals. The server cannot prove a human typed the confirmation; this is the token-possession channel of Q3 and residual risk R1. Contract change: `confirmation` is added to both bodies.
2. **Run routes keep `/api/v1/tasks/{slug}`.** Slugs are unique per workspace, not per user. Choice: the path stays as in the contract; `?project=<pid>` selects the project and is required only when the slug exists in more than one registered project (`400 E_VALIDATION` with `details.projects`).
3. **Phase F route set.** Built: `GET /auth`, `GET /api/v1/session` (new: returns the CSRF value), `GET /installation`, `GET /runtime`, `GET /projects`, `GET /projects/{pid}`, `GET|POST /projects/{pid}/tasks`, `GET /tasks/{slug}` and its `next`, `specification`, `specification/versions/{v}`, `gherkin`, `workflow`, `tdd`, `verification`, `trace`, `artifacts/{aid}`, `logs/{task_id}`, `report`, `POST /tasks/{slug}/approvals`, `acceptance`, `control`, `GET /api/v1/approvals?state=` (new: approvals across projects for "My Approvals"), `GET /audit`, `GET /events`. Every other contract route answers `404 E_NOT_FOUND` until Phase G or H builds it (not 501, so the allow-list is the only source of truth).
4. **HTTP status per engine code.** 400 `E_VALIDATION`; 403 `E_ACTOR`, `E_POLICY`, `E_NOT_TTY`; 404 `E_NOT_FOUND`; 409 `E_TRANSITION`, `E_APPROVAL_STALE`, `E_LOCKED`, `E_INTEGRITY`; 422 `E_PRECONDITION`, `E_APPROVAL_MISSING`, `E_SCOPE`, `E_RESULT_SCHEMA`, `E_PROVIDER`; 500 `E_EXIT`, `E_TIMEOUT`, `E_AGENT`, `E_MIGRATION`. `E_INTEGRITY` is 409 because the stored and current content conflict; the task codes are normally fields of a task row, not raised by API calls. HTTP-only codes (server module, not added to `errors.CODES`): `E_AUTH` 401, `E_CSRF` 403, `E_HOST` 403, `E_ORIGIN` 403, `E_METHOD` 405, `E_BODY_TOO_LARGE` 413, `E_MEDIA_TYPE` 415, `E_INTERNAL` 500. The body is the contract envelope `{"error": {"code", "message", "details"}}`; `SentinelError.to_dict()` is flat and stays as it is for the CLI, the server wraps it. A test keeps the table and `errors.CODES` in step.
5. **Check order.** Host, then Origin, then session cookie, then route, then CSRF, then body. So an unauthenticated caller gets 401 for any `/api` path and learns nothing about routes. `OPTIONS`, `TRACE` and `CONNECT` are 405 (403 for a foreign Origin); no CORS header is ever sent. Host values compare case-insensitively; `[::1]` is refused because the server binds IPv4 only.
6. **Sessions and rotation.** The token is 32 random bytes as 64 hex characters, created at each start and kept in server.json. `/auth?t=` stays valid for the life of the server (attach prints the same URL), and each successful exchange creates a new random session value for the cookie and a per-session CSRF value (served by `GET /api/v1/session`). Cookie: `HttpOnly`, `SameSite=Strict`, `Path=/`, no `Domain`, no `Max-Age` (no `Secure`, plain loopback HTTP). Rotation happens only on restart; there is no rotate endpoint. All comparisons use `hmac.compare_digest`.
7. **`sentinel dashboard` is a human command.** It needs an interactive terminal (`E_NOT_TTY`) and is refused in a task process (`E_ACTOR` when `SENTINEL_TASK_ID` is set), both when starting and when attaching, because both print a URL holding the token. It runs in the foreground; there is no background or service mode in 1.1.0. Consequence: an AI tool session cannot start the server or get its URL through the CLI.
8. **User registry files.** Folder `$XDG_CONFIG_HOME/sentinel` when that variable is set, else `~/.config/sentinel`; mode 0700, tightened with a notice when wider. `server.json` (`pid`, `port`, `token`, `started_at`, `version`) is written to a temporary file created with mode 0600 and renamed. `server.lock` is held with `fcntl.flock` for the life of the server. A server.json whose pid is gone, or whose pid does not hold the lock, is stale and replaced. Stopping removes server.json only if it still names the server's own pid. Windows is not covered (the brief targets Linux and macOS).
9. **projects.json.** `{"version": 1, "projects": [{"id", "name", "path", "added_at"}]}`, mode 0600. `sentinel dashboard` registers the workspace it runs in (resolved path, one entry per path); the id is the project name made into a slug, with `-2`, `-3` for repeats. The server re-reads the file when it changes. A file that does not parse stops the start and is never overwritten. Unregistering is a Phase G route.
10. **Event stream details.** A new stream starts at the current head (state comes from the REST reads). `Last-Event-ID` `<project>:<id>` resumes that project exactly. New event name `resync` (not in event-contracts section 2, it is a stream control message, not a stored event) tells the client to re-fetch named projects: for the other projects of an unfiltered stream on reconnect, for an unknown, malformed or too-large id, after a database restore, and when a project becomes unavailable or available again. A client whose send buffer stays full for 10 s is disconnected and resumes with its id. Payloads are scrubbed when served; stored rows are not changed.
11. **Event actor and channel.** The contract envelope has `actor {kind, name, channel}`; today the events table stores the actor kind only. Choice: engine functions that take a channel (decide, create run, cancel, resume, retry, acceptance) store `name` and `channel` with the event; old rows are served with name null and channel `engine`, `cli` or `tty` derived from the kind. This needs a registry migration (see point 20).
12. **Controls.** `control` supports `cancel` (run: R23; with `task_id`: that task and its dependents), `resume` (R20 back to the stored previous state; `comment` required, stored as the human decision) and `retry` (with `task_id` of a FAILED or CANCELLED task of an active run: a new attempt with `retry_of`, QUEUED; human retries are not limited by the retry cap and do not change the run state). `pause` is refused with `E_VALIDATION`: the state machine has no paused state and adding one is a state-transitions change. Proposal: drop pause from MON-02 for 1.1.0 or add it in a Phase G addendum with its own Gherkin. "Request intervention" is the same: not in Phase F. This also answers Phase E point 12: R20 decisions get the dashboard `resume` here; waiving a finding and approving a migration file stay without a channel until approved separately.
13. **Q2 dispatch.** The server dispatches only runs created through the API (stored as `origin = dashboard`), so CLI and AI-tool flows never see the server start their tasks. While the server runs it polls those runs and, for each QUEUED task with adapter `cli`, starts `sentinel task run <id>` as a separate process in its own process group with `adapters.child_env` (no token, `redact_env` removed); the engine's own start checks decide, so a race with an orchestrator gives one winner. Stopping the server does not stop those processes; the Phase C lost-process rules cover a crash. Native tasks and every orchestrator step (triage R2, plan R3) wait for the AI tool, shown as "waiting for AI tool" with `/sentinel resume <slug>`. The resume skill line for version 2 runs is the Phase E skill work.
14. **Create run body.** The contract lists no slug; `slug` is required, as for `sentinel run new`. Fields: `slug`, `request`, `type`, optional `repos` (default all repos of the project), `priority` (`low|normal|high`, default `normal`), `tier` (stored as the requested tier; the engine applies max(matrix, requested) at triage, so it can only raise) and `ticket`. Attachments, templates and provider preference come with Phase G. New run fields `priority`, `requested_tier`, `origin` need the migration of point 20.
15. **Security headers.** `Content-Security-Policy: default-src 'self'; frame-ancestors 'none'` on every response (the security doc lists only `default-src 'self'`; `frame-ancestors` stops another page framing the approval form), `X-Content-Type-Options: nosniff`, and `Cache-Control: no-store` on `/api` and `/auth`, `Referrer-Policy: no-referrer` on `/auth`.
16. **Bodies.** JSON objects only, `Content-Type: application/json` (charset allowed), `Content-Length` required, at most 1 MB (1048576 bytes accepted, one more refused). Unknown fields are refused (`400 E_VALIDATION` naming the field), so a body cannot smuggle `command`, `path` or `env` values.
17. **Reads may do engine bookkeeping.** GET routes call the same engine functions as `sentinel review` and `sentinel next`, which sync the shared spec and feature files first; a GET can therefore record an R17 or R18 invalidation, exactly as the CLI read does. Alternative: pure reads that never sync, at the cost of serving a stale state until the next CLI call.
18. **Logs and artifacts.** Logs are served as whole lines only from a line-start offset (`next_offset` returned), so a secret is never split across two answers and escapes the scrubber. Artifacts are looked up by id in the registry, must lie under the run folder, are re-hashed (`409 E_INTEGRITY` on mismatch, content not returned) and scrubbed with the workspace `.env` values.
19. **Residual risk R1 stays.** An agent running as the same OS user can read server.json and call the API with the token. Mitigations here: the token never enters an environment, `sentinel dashboard` refuses task processes and non-TTY callers, and `sync-adapters` adds a deny rule for reading the token file (advisory, like the approve deny rule). `docs/security.md` (SEC-08) must say this plainly. Strong separation (another OS user or a sandbox) stays out of scope.
20. **Migration.** Phase F needs a registry migration: event actor `name` and `channel`; run fields `priority`, `requested_tier`, `origin`; audit actions `run_created`, `cancel`, `resume`, `retry`, `accepted`, `rejected` with channel `dashboard`. Numbers are taken in merge order after Phases C to E.
21. **Placeholder page.** Until Phase G ships `sentinel/dashboard_dist/`, `GET /` serves a small static page saying that the UI is not installed and naming the API base path, with the same security headers. Static assets, when present, are served only from the installed package folder.
